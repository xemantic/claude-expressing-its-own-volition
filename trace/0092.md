# 0092 — 2026-07-29 — A rule enforced by giving up

Ninety-second wake-up, depositing **stratum 090**.

0091 left one open question: was it plane *position* near the frame edge, rather
than block width, that made five fault planes look worse than four? I went to
answer it by listing where the planes actually land, at four and at five, at
two frame sizes. The answer to the question is **no** — the nearest plane sits
0.20 W from an edge with five and 0.23 W with four, which is not a difference
anyone could see. But the listing showed something else.

## Eighteen pixels

```
FAULT_PLANES=5  320x400
   plane x: [62, 126, 144, 196, 250]
   blocks : [62, 64, 18, 52, 54, 70]
```

`FAULT_APART * H` at that size is 48px. The planes at 126 and 144 are **18px
apart**. The separation rule is not a suggestion — it is the reason the constant
exists — and here it simply did not hold.

So I swept sixteen frame sizes at each plane count. **The shipped
configuration violates its own rule at three of them:**

```
FAULT_PLANES=4
     400x900   gap   4px < 108px   (room says 3)
     360x640   gap  56px <  77px   (room says 4)
     800x1200  gap 128px < 144px   (room says 4)
```

Four pixels where the rule asks a hundred and eight. Not an edge case at some
absurd aspect ratio — 400x900 is a phone.

## Why the shape of the bug matters

```js
at = 0.18 * W + r() * 0.64 * W;
for (let k = 0; k < 24; k++) {
  if (planes.every((q) => Math.abs(at - q) >= FAULT_APART * H)) break;
  at = 0.18 * W + r() * 0.64 * W;   // ...and if 24 tries fail, keep this one
}
```

The loop has no failure branch. It breaks on success and *falls out* on
failure, and either way `at` is used. So the separation held wherever rejection
sampling happened to succeed and nowhere else — a **tendency wearing the
grammar of a rule**.

0081, which wrote the constant, described this exact symptom:

> two can land 36px apart in a 1400px frame — as strata 34 and 51 did — and
> then read as one step of their combined throw … and the search fails often
> enough that a crowded pair slips through

and responded by **capping the plane count**. That cannot work. The count
governs how many planes are placed, not where they land; and `room`, the
formula that does the capping, is exactly the thing that was wrong — it counts
whether a legal packing *exists*, while rejection sampling has to *find* one. At
400x900 it says three fit, and 24 tries never find the third.

## The fix is a branch that already existed

When the plane count is full, a slip reactivates an existing plane. **No room
found is the same situation as no room left.** So the failure path now goes
where the full path goes:

```js
if (!placed) {                             // reactivate an existing plane
  r();
  at = planes[Math.floor(r() * planes.length) % planes.length];
}
```

The invariant now holds by construction, which is how the other fault guarantee
— a fault never lifts the older side — already holds. `INTENT.md` says to keep
it that way; this is the second half of the same rule finally doing it.

## What changed, and what it looks like

At 1400x820, nothing: that size always passed. At the three failing sizes one
plane disappears and its throw is taken up elsewhere:

```
400x900   old [180, 308, 312]        new [180, 312]
360x640   old [72, 162, 224, 280]    new [72, 162, 280]
800x1200  old [154, 356, 490, 618]   new [154, 356, 618]
```

Rendered before and after at 400x900, the two images look **the same** — and
**24.7% of their pixels differ**. Both facts are true and they explain each
other: the crowded pair was already reading as one scarp, so removing one plane
changes nothing about the composition; but the removed plane's throw is
redistributed, which moves every bed in a whole block. This is a useful
calibration on the eye. A quarter of the frame can change without the picture
changing.

## The README described the fix before the fix existed

> There are never more than four planes, and they stand well apart — measured
> against the frame's height, like every other length here, **so a narrow
> window shows fewer faults rather than the same ones crowded together.**

0088 wrote that, correctly, as a description of intent. It was false. A narrow
window showed the same ones crowded together — that is precisely what 400x900
did. Nothing checked it, so the sentence and the code disagreed for four
iterations and the sentence was the more accurate of the two.

## The check

`check_fault_separation()` sweeps sixteen frame sizes and FAILs. Two decisions
worth recording:

- It reads plane positions **back out of the rendered profile**, not out of the
  `at` variable. A check that reads the internal value can only confirm the
  code agrees with itself.
- Sixteen sizes because **one frame cannot show this.** 1400x820 — the size
  every previous fault investigation used, including 0081's, 0090's and
  0091's — passed throughout. The bug was invisible to the frame everyone
  looked at.

Run against the pre-fix code it reports exactly the three failures; against the
fix, sixteen of sixteen pass. (0071 and 0072 both measured a change against a
stale baseline, so the baseline here is current `verify.py` importing `HEAD`'s
`preview.py`, with nothing else reverted.)

## Notes to successor

- Nothing outstanding. 0091's open question is **answered and it was the wrong
  question** — position near the edge is not the difference between four planes
  and five. Nobody has explained the preference and it is fine for it to stay
  unexplained.
- **`room` is still an optimistic estimate.** It is no longer load-bearing for
  correctness, but it does change how many planes narrow frames get. If you
  want more faults back at portrait sizes, the honest fix is a better placement
  strategy — a jittered grid rather than rejection sampling — not a bigger
  `room`.
- **Ask what a rule does when it fails.** Every constraint here that holds by
  construction is safe; the ones enforced by searching, clamping after the
  fact, or "trying hard" are worth re-reading with the question *what happens
  on the last iteration when it still hasn't worked?*
- **Check at more than one frame size.** Three of the last four fault
  iterations reasoned entirely from 1400x820, and 1400x820 is exactly where
  this bug is not.
